# What can we take from dotnet-podcasts?

Research for ticket `01-dotnet-podcasts-lessons`. Primary source: [microsoft/dotnet-podcasts](https://github.com/microsoft/dotnet-podcasts), read at commit [`5ee8be2`](https://github.com/microsoft/dotnet-podcasts/tree/5ee8be2990b81eb681bbd100875c263aaa5ab68a) (2 May 2024). GitHub says the repository was "archived by the owner on May 6, 2024. It is now read-only." Every project in it targets `net7.0`, for example [`Podcast.Client.csproj`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Client/Podcast.Client.csproj) and [`Podcast.API.csproj`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.API/Podcast.API.csproj).

All file links below point to that commit. Short form: `src/...` means `https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/...`.

## Short answer

**Copy:**

1. **The player layout.** One `<audio>` element and the player bar sit in `MainLayout`, outside `@Body`. Pages never own the audio. ([`MainLayout.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/MainLayout.razor))
2. **A single player-state service.** One service holds the current item, play/pause, volume, time and rate, and raises events. The audio component and the player bar both subscribe to it. Pages only call `Play(...)`. ([`PlayerService.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Data/PlayerService.cs))
3. **Thin JS interop.** A seven-line ES module wraps `HTMLMediaElement`, and C# loads it lazily with `import` ([`audioJsInterop.js`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Components/wwwroot/audioJsInterop.js), [`AudioInterop.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Components/AudioInterop.cs)). Custom Blazor event types carry `timeupdate` and `durationchange` from the element back to C# ([`customEvents.js`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/wwwroot/js/customEvents.js)).
4. **Minimal API organisation.** Route groups go in one static `Map…Api` extension per resource, with handlers that return `TypedResults` ([`Routes/`](https://github.com/microsoft/dotnet-podcasts/tree/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.API/Routes)).

**Avoid:**

1. **The microservice sprawl.** The sample has six deployables plus Orleans, a queue and two databases. KleinGeld needs one API, one front end and one database, wired by Aspire.
2. **Its audio delivery model.** `<audio src>` points straight at a third-party RSS enclosure URL. Covers live in a *public* blob container. KleinGeld is invite-only, so Track audio has to go through an authorised path, either an API endpoint with range processing or short-lived signed URLs.
3. **Its .NET 7 hosting model.** It uses `_Host.cshtml`, the Component Tag Helper, `blazor.webassembly.js` and the hosted Blazor WebAssembly layout. .NET 8+ Blazor Web Apps replace all of these.
4. **Client-only personal data.** "Listen later" and subscriptions live in `localStorage`. KleinGeld Playlists belong to a Member and must be stored on the server.
5. **Paid always-on Azure services.** It uses App Service S1/B1 plans, SQL Server, Orleans on Table storage, a Container Registry and Log Analytics. At around 50 Members most of these are unnecessary or have cheaper equivalents.

## 1. How the web app keeps audio playing across navigation

### What dotnet-podcasts does

- **Render mode: global WebAssembly, prerendered.** The server's Razor Page `_Host.cshtml` renders the whole router as one root component: `<component type="typeof(App)" render-mode="WebAssemblyPrerendered" />` ([`src/Web/Server/Pages/_Host.cshtml` L8](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Server/Pages/_Host.cshtml#L8)). The layout loads `blazor.webassembly.js` ([`_Layout.cshtml` L44](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Server/Pages/_Layout.cshtml#L44)). After the first load, every navigation is client-side routing inside one WebAssembly runtime, so the layout and its components stay alive.
- **Component placement.** `MainLayout.razor` renders `<PlayerBar />` and `<Audio />` as siblings of `@Body` ([`MainLayout.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/MainLayout.razor)). The router swaps only `@Body`, so the `<audio>` element is never torn down.
- **State.** `PlayerService` is a plain C# class with properties whose setters raise `Action<T>` events: `EpisodeChanged`, `PlayingChanged`, `TimeSought` and so on ([`PlayerService.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Data/PlayerService.cs)). The client registers it with `AddSingleton<PlayerService>()` ([`src/Web/Client/Program.cs` L19](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Client/Program.cs#L19)). In WebAssembly a singleton lives for one browser tab.
- **Audio component.** `Audio.razor` renders `<audio @ref=… src="@url" oncustomtimeupdate=… oncustomdurationchange=… onplay=… onpause=…>`. It subscribes to `PlayerService` events and pushes commands to the element through `IAudioInterop`. Element events update `PlayerService`, which re-renders the bar ([`Audio.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/Player/Audio.razor)).
- **Player bar.** `PlayerBar.razor` subscribes to the same events and calls `InvokeAsync(StateHasChanged)`. It feeds a presentational `FloatingPlayer` component ([`PlayerBar.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/Player/PlayerBar.razor)).
- **JS interop.** The JS module exports `play`, `pause`, `setMuted`, `setVolume`, `setCurrentTime` and `setPlaybackRate`, each one line ([`audioJsInterop.js`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Components/wwwroot/audioJsInterop.js)). C# imports it once through `Lazy<Task<IJSObjectReference>>` and disposes it in `DisposeAsync` ([`AudioInterop.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Components/AudioInterop.cs)).
- **Custom events.** `Blazor.registerCustomEventType('customtimeupdate', { browserEventName: 'timeupdate', createEventArgs: … })` and the matching `[EventHandler]` attributes let Razor bind media events with typed args ([`customEvents.js`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/wwwroot/js/customEvents.js), [`Events/EventHandlers.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Events/EventHandlers.cs)). The script tag is placed after `blazor.webassembly.js` ([`_Layout.cshtml` L45](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Server/Pages/_Layout.cshtml#L45)).

### Small defects not to copy

- The server also registers `AddSingleton<PlayerService>()` ([`src/Web/Server/Program.cs` L23](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Server/Program.cs#L23)). On the server a singleton is shared by every request. Here it only feeds prerendering, so it is harmless. In an Interactive Server or Auto app it would leak one Member's player state to everyone. Per-user state on the server must be scoped.
- `timeupdate` fires several times a second. Each event invokes C#, sets `CurrentTime` and re-renders `PlayerBar` ([`Audio.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/Player/Audio.razor), [`PlayerBar.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/Player/PlayerBar.razor)). That is fine in WebAssembly. Over an Interactive Server circuit it would be a round trip per tick.
- `AudioInterop.StopAsync` calls `element.stop()` ([`audioJsInterop.js`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Components/wwwroot/audioJsInterop.js)). [`HTMLMediaElement`](https://developer.mozilla.org/docs/Web/API/HTMLMediaElement) has no `stop()` method. The method is never called.
- Volume, mute and the current item are not persisted, so a full reload loses the player ([`PlayerService.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Data/PlayerService.cs)).

### Mapping onto our two front-end options

**Option A: Blazor Web App, global Interactive WebAssembly.** This is the direct descendant of the sample. In .NET 8+ you set the mode on `Routes` and `HeadOutlet` in `App.razor` (`<Routes @rendermode="InteractiveWebAssembly" />`). The `Router` then "propagates its render mode to the pages it routes". With global interactivity the layout and pages move into the `.Client` project ([Render modes: Apply a render mode to the entire app](https://learn.microsoft.com/aspnet/core/blazor/components/render-modes?view=aspnetcore-10.0#apply-a-render-mode-to-the-entire-app)). The sample's pattern carries over almost unchanged: player components in `MainLayout`, a singleton `PlayerService` in the client, and a JS module for the element. Two changes:

- Register custom event types from a JS initializer. In a Blazor Web App this is `{ASSEMBLY}.lib.module.js` exporting `afterWebStarted(blazor)`, not a script tag after `blazor.webassembly.js` ([Event handling: Custom event arguments](https://learn.microsoft.com/aspnet/core/blazor/components/event-handling?view=aspnetcore-10.0#custom-event-arguments)).
- Interactive modes prerender by default ([Render modes: Prerendering](https://learn.microsoft.com/aspnet/core/blazor/components/render-modes?view=aspnetcore-10.0#prerendering)). Keep the server-side registration of player state scoped, or disable prerendering for the player.

**Option B: static SSR + enhanced navigation + `data-permanent` player.** With static SSR "interactivity isn't enabled" ([Render modes: Static SSR](https://learn.microsoft.com/aspnet/core/blazor/components/render-modes?view=aspnetcore-10.0#static-server-side-rendering-static-ssr)). Nothing like `PlayerService` or `Audio.razor` can run in C# on the client. Enhanced navigation does a `fetch` and "patches the response content into the page's DOM". It "may undo dynamic changes to the DOM if the updated content isn't part of the server rendering. To preserve the content of an element, use the `data-permanent` attribute." ([Navigation: Enhanced navigation and form handling](https://learn.microsoft.com/aspnet/core/blazor/fundamentals/navigation?view=aspnetcore-10.0#enhanced-navigation-and-form-handling)). What carries over from the sample:

- **The placement idea.** Render the player container, holding `<audio>` and the bar markup, once in `MainLayout` and mark it `data-permanent`.
- **The state-service idea, in JavaScript.** The sample's `PlayerService` and `audioJsInterop.js` merge into one plain JS module that owns the element and the bar's DOM. Load it through an `afterWebStarted` JS initializer. Page-specific `<script>` tags are not re-run on enhanced navigation, so wire "Play this Track" buttons with event delegation or `enhancedload` listeners ([JS with static SSR](https://learn.microsoft.com/aspnet/core/blazor/javascript-interoperability/static-server-rendering?view=aspnetcore-10.0)).
- **What does not carry over.** Custom Blazor event types and `IJSObjectReference` interop exist only for interactive components.
- **Escape hatch.** A link marked `data-enhance-nav="false"` causes a full reload ([Navigation](https://learn.microsoft.com/aspnet/core/blazor/fundamentals/navigation?view=aspnetcore-10.0#enhanced-navigation-and-form-handling)), which stops the audio. Keep that attribute off in-app links.

**Verdict for the front-end ticket.** The sample is evidence *for* Option A's ergonomics: the player is about 150 lines of C# plus 7 lines of JS. Option B can copy the placement and the single-owner state design but must rewrite the player in JS. The sample does not prove Option B works.

It ships three solutions ([`NetPodcast.sln`, `NetPodcast.Services.sln`, `Podcast.Web.sln`](https://github.com/microsoft/dotnet-podcasts/tree/5ee8be2990b81eb681bbd100875c263aaa5ab68a)) and roughly 15 projects:

| Other clients | MAUI app, MAUI Blazor Hybrid app, `SharedMauiLib`, Power Apps | [`README.md`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/README.md) |

The front end needs API and hub URLs configured by hand in *both* Server and Client `appsettings.json` ([`src/Web/README.md`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/README.md)).

Two RCLs exist so the MAUI Blazor Hybrid app can reuse the pages. The web `Podcast.Shared` DTOs are hand-written duplicates of the API's `Podcast.Infrastructure` DTOs: compare `src/Web/Shared/Episode.cs` with `src/Services/Podcasts/Podcast.Infrastructure/Data/DTOs/EpisodeDto.cs`. The MAUI app has a third copy under `src/Mobile/Models`.

### What we would simplify

- **One API project, one front end, one AppHost, one ServiceDefaults.** Aspire replaces docker-compose and the hand-copied URLs. The AppHost declares resources and passes them with `WithReference(...)`/`WaitFor(...)` ([Aspire: Set up Azure Blob Storage in the AppHost](https://aspire.dev/integrations/cloud/azure/azure-storage-blobs/azure-storage-blobs-host/)). ServiceDefaults provide OpenTelemetry, health checks, service discovery and HTTP resilience ([Aspire: C# Service Defaults](https://aspire.dev/get-started/csharp-service-defaults/)).
- **No RCLs for pages and components.** We have no MAUI or hybrid client. A Blazor Web App has a server project and, for WebAssembly, a `.Client` project ([Render modes](https://learn.microsoft.com/aspnet/core/blazor/components/render-modes?view=aspnetcore-10.0#apply-a-render-mode-to-the-entire-app)). That is enough.
- **One shared contracts project, or none.** Share one set of request/response records between API and front end instead of three hand-copied model sets. If the front end is static SSR it can call the API server-side and use the same contracts project.
- **Domain logic in the API project at first.** Split out a domain or infrastructure project only when there is a real second consumer. The sample's four-project Clean Architecture split for Listen Together is not something we need.
- **No separate worker deployables.** The sample's workers exist for RSS polling and queued feed ingestion. We have no feeds. If upload post-processing (Track transcoding, duration extraction) needs background work, start with a `BackgroundService` hosted in the API.

## 3. How audio is served to the player

### What dotnet-podcasts does

- **Direct third-party URLs.** An Episode's `Url` is the RSS `<enclosure url>` copied verbatim at ingestion (`var url = item.Enclosure!.Url`, [`Mapper.cs` L31](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.Infrastructure/Http/Feeds/Mapper.cs#L31)). It is stored as a string ([`Data/Models/Episode.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.Infrastructure/Data/Models/Episode.cs)) and bound straight to `<audio src="@url">` ([`Audio.razor`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Pages/Shared/Player/Audio.razor)).
- **No proxy, no range handling.** The API has no audio endpoint at all: `EpisodesApi` returns metadata only ([`EpisodesApi.cs`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.API/Routes/EpisodesApi.cs)). Seeking relies on the third-party host honouring `Range` requests from the browser.
- **Public blob container for covers.** The cover-image script creates the container with `--public-access blob` ([`deploy/Images/Deploy-Images.ps1`](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/deploy/Images/Deploy-Images.ps1)). The updater rewrites image URLs to `{Storage__Images}{showTitle}{ext}` ([`Mapper.cs` L37–43](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Services/Podcasts/Podcast.Infrastructure/Http/Feeds/Mapper.cs#L37-L43), [`api.bicep` L314](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/deploy/Services/api.bicep#L314)).
- **No offline audio.** The PWA service worker caches only app assets (`.dll`, `.wasm`, `.js`, images, and so on), not audio ([`service-worker.published.js` L14](https://github.com/microsoft/dotnet-podcasts/blob/5ee8be2990b81eb681bbd100875c263aaa5ab68a/src/Web/Client/wwwroot/service-worker.published.js#L14)).

### What this means for KleinGeld

None of this delivery model transfers. Podcast audio is public and hosted by someone else. KleinGeld Tracks are Member-only, uploaded by Artists, and subject to Takedown. So:

- **Copy only the client side.** A plain `<audio src="…">` with the browser doing range requests is still the right player. The question is what URL it gets.
- **Never use a public container for Track audio or cover art.** Anyone with the link could stream a Taken-down Release.
- **Simplest authorised option: an API endpoint that streams the file with range support.** ASP.NET Core Minimal APIs support this directly. With `enableRangeProcessing: true`, a `Range: bytes=…` request returns `206 Partial Content` with `Content-Range`, unsatisfiable ranges return `416`, and `If-Range` is honoured when an ETag or last-modified value is set ([Minimal API responses: range requests](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/responses?view=aspnetcore-10.0)). The endpoint can check the Member's session and the Release state (Published, not Taken down) on every request. At around 50 Members, the bandwidth through the app is not a concern.
- **Alternative: short-lived signed blob URLs.** These offload bandwidth but complicate Takedown: a URL stays valid until it expires. They are worth a follow-up only if streaming through the API proves too costly. (Not researched here.)
- **Cookie auth is easiest for `<audio>`.** The element cannot attach a bearer token, so a same-origin cookie or a signed URL is required. This should feed the auth ticket.

I did not look up prices. The point is the *count* of always-on resources (two SQL databases, two App Service plans, a container environment with a minimum-1 API replica, plus registry and workspace), not any particular SKU.
