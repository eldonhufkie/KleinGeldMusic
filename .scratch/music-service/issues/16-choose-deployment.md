# Choose how new versions are deployed

Type: grilling
Status: resolved
Assignee: Eldon Hufkie
Blocked by: 15

## Question

Using [Deploying to a TrueNAS custom app from Azure DevOps](15-deploy-to-truenas-research.md), decide how a new version is built, stored, and applied on TrueNAS: the container registry, what triggers a deploy (every merge to `develop`, a release branch, a manual button), how secrets are kept, and how EF Core migrations run.

The research also raises: whether to upgrade TrueNAS (24.10 is archived; path 24.10 → 25.04 → 25.10) before the first deploy, since 24.10 can't store private-registry credentials; how Aspire's `.env`-based compose output is fed to a TrueNAS custom app; and how the API waits for Postgres given `WaitFor` maps only to `service_started`.

## Answer

Decided by Eldon Hufkie on 2026-10-31 in a grilling session.

### Part 1: running Aspire's output on TrueNAS

Decided by Eldon Hufkie in a grilling session, while TrueNAS was being upgraded from 24.10 (target 25.10).

**Feeding Aspire's output to TrueNAS**
- **Include stub**: the TrueNAS custom app's YAML is a fixed stub, pasted once, that only `include:`s Aspire's generated `docker-compose.yaml` with `env_file: [secrets.env, release.env]`, all in a dataset folder (e.g. `/mnt/<pool>/apps/kleingeld/`). A deploy replaces files in that folder and redeploys. Rejected: rendering full YAML in CI and pushing via `app.update` (secrets visible in the TrueNAS edit screen). **Verify first after the upgrade**: 25.10 accepts `include:` with an absolute `env_file` path.
- **Secrets**: each secret is declared once in the AppHost as a secret parameter (`AddParameter(..., secret: true)`). Development values live in the AppHost's user secrets (`secrets.json`, `Parameters:<name>`). Production values live in a root-only `secrets.env` (mode 600) on the dataset, written by hand once via System → Shell or SSH, using the variable names Aspire generates. The dataset is never shared over SMB/NFS; a copy of the values is kept in a password manager. Changing a secret: edit `secrets.env`, redeploy. Nothing secret passes through Azure DevOps.
- **Image tags**: each deploy pushes images tagged with the build number or commit SHA, set in a non-secret `release.env` written by the workflow. Never `latest`. Rollback: change the tag in `release.env`, redeploy.
- **Data**: PostgreSQL data and Data Protection keys are bind-mounted from host-path folders on TrueNAS datasets (set in the AppHost for publish mode), not Docker named volumes, so ZFS snapshots cover them (see [Backups for the database and audio](14-backups.md)).
- **No hand edits**: every compose change (healthchecks, restart policies, mounts) is made in the AppHost via `PublishAsDockerComposeService` / `ConfigureComposeFile`. The compose file is generated by `aspire publish` in CI and not committed.

**How the API waits for PostgreSQL**
- **Migrator worker**: a small worker project applies EF Core migrations and exits; the API uses `WaitForCompletion(migrator)` (`service_completed_successfully`). A failed migration keeps the API down until a fix is deployed, which is acceptable. Rejected: `MigrateAsync()` at API startup; Aspire's migration-bundle integration (prerelease only).
- **Readiness**: PostgreSQL gets a `pg_isready` healthcheck and the migrator depends on it as `service_healthy` (via `ConfigureComposeFile`, because `WaitFor` only produces `service_started`). The API and migrator also use Npgsql/EF Core connection retries (`EnableRetryOnFailure`) for PostgreSQL restarts while running.
- **Restart policies**: `unless-stopped` for long-running services; `"no"` for the migrator, so it runs once per deploy.
- **Scaling note**: the migrator runs once per deploy however many API copies run, so it scales as is. At a much larger audience the limits are the single home server and its single PostgreSQL. Revisit hosting if peak-time slowdowns appear, home outages become unacceptable, or Members grow into the hundreds.

### Part 2: getting a version there

- **TrueNAS 25.10 only**: finish the upgrade path (24.10 → 25.04 → 25.10) before the first deploy. Check on the box before any workflow work: `include:` with an absolute `env_file` path works in a custom app.
- **Source and CI move to GitHub**: the repository moves from Azure DevOps to a **public** GitHub repository (`git push --mirror`, research branches included); CI/CD on **GitHub Actions**. Push protection (secret scanning) is turned on. Reasons: portfolio value, the official Tailscale action, unlimited Actions minutes and free Environment reviewers on public repos. The code holds no secrets and no audio.
- **Registry**: **GitHub Container Registry, public packages**. CI pushes with `GITHUB_TOKEN`; TrueNAS pulls without credentials. Each workflow run keeps the last 10 versions per image (`actions/delete-package-versions`). Rejected: Azure Container Registry (~$5/mo); the existing private registry on TrueNAS (would need HTTPS via `tailscale serve`, push/pull logins and its own clean-up).
- **Applying an update**: a GitHub-hosted runner joins the tailnet as an ephemeral `tag:ci` device via `tailscale/github-action` (OAuth client). The Tailscale ACL lets `tag:ci` reach only TrueNAS port 22. It SSHes in as a dedicated `deploy` user whose key is locked to a forced command, `deploy.sh`, accepting only `deploy test <tag>` or `deploy prod <tag>` plus the generated `docker-compose.yaml`; the script writes that and `release.env` into the app's folder and runs `midclt call app.redeploy <app>`. GitHub holds only the Tailscale OAuth secret and that SSH key. Rejected: a self-hosted runner on TrueNAS (permanent, needs updates, root via `docker.sock`); Watchtower (archived).
- **Branches and trigger**: work on `develop`; every push and PR builds and runs tests, never deploys. A release is a PR from `develop` into a new `main` branch. A merge to `main` builds and pushes one tag, deploys it to **Test** automatically, then waits on a GitHub `production` Environment with Eldon as required reviewer (the "Live" button) before deploying the **same tag** to **Production**. Nothing is rebuilt between Test and Production.
- **Test**: a second custom app, `kleingeld-test`, on the same TrueNAS: its own dataset folder (`secrets.env`, `release.env`), PostgreSQL and Blob container; reachable only on the tailnet via `tailscale serve`, never Funnel. Email goes to a MailPit container on the tailnet, never Gmail. Data starts empty plus a seed step (an Admin, a couple of Members, a few sample Releases); never a copy of Production, which would put real Members' emails and unreleased music in a second place.
- **Vercel**: out of scope (see the map). Hosting the front end there would break the same-origin login cookie the audio stream relies on; a portfolio showcase site sits outside the destination.
- No ADR: each choice is cheap to reverse, apart from making the repository public, which is a one-way door taken knowingly.
